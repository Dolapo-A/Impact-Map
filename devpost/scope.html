Impact Map

A tool that takes a pull request's changed files and shows you the blast radius — an animated, evidence-backed graph of everything those changes can reach.

The Unique Kernel

An impact map with evidence, not a review. Every claim traces back to a real dependency edge you can click and verify. No LLM, no opinions, no "an AI thinks this might be risky." If you deleted the graph and the explanations, there'd be no tool left — because the graph is the product, not a view onto a model.

Who It's For

Primarily the developer who just opened their own PR. They know what they changed but not what they forgot; the question is "what else did I break?" Today they answer it by rereading the diff and guessing — or by finding out in CI, or in production.

Secondarily the reviewer looking at someone else's PR, who needs to orient fast. Same map, read differently.

Both, deliberately. The graph view is genuinely shared — the same expansion answers "what did I forget?" and "where do I start reading?" What differs is the text per node, not the view. v1 builds one graph with one explanation style, leaning author-side. Reviewer-optimized annotation is later.

The Core Loop

  1. Open the tool and point it at a PR, or a set of changed files.
  2. The graph loads — the repository's dependency structure.
  3. It animates outward from the changed files: nodes expand, edges draw themselves, the affected cluster lights up while everything else stays dim.
  4. Click any node to read why it matters and whether it's covered by tests.

You come back because it caught something you didn't think about.

The Shape Of It

What "Working" Looks Like

You paste or point at a PR. The graph loads. Then it animates: nodes fly outward from the changed files, edges draw themselves in, and the affected cluster lights up while everything else stays dim. You click one node and it tells you why it matters and whether it's tested.

That expansion-and-light-up is the beat the whole demo video is built around — about 45 seconds, and it sells the entire idea.

And since no LLM is involved, "working" also means the graph is genuinely correct: every edge is a real import, verifiable by clicking through to the file.

Why This Matters To The Learner

The idea started as a response to a specific frustration: years of using version control without ever fully grasping it — "over this period of time, I've not fully grasped it." The tool is built to make the shape of a codebase and a change visible in a way git never was.

TypeScript was chosen deliberately as the language they most want to work in. A real stake in this build, not an implementation detail.

The aim beyond the demo: to be able to scope a project and write a PRD for one themselves. This project is the vehicle — scope it here, define it in 3-prd, build against it in 5-build, and find out whether the requirements actually held up.

The POC Boundary

In

  • Input: one pull request, or a set of changed files
  • Parse the JavaScript/TypeScript dependency graph — imports, exports, re-exports, cross-file references
  • Walk outward from the changed files to find what they reach
  • Detect and handle circular imports
  • Render as an interactive 2D graph: nodes are files, edges are imports
  • Animate the outward expansion and highlight affected nodes
  • Click a node → why it matters, and whether it's covered by tests
  • One small sample repository shipped with the tool, with genuinely interesting structure
  • Repo path is configurable, so it can be pointed at a real repository

Explicitly not in — the AI. Dependency tracing is deterministic; an LLM would be slower, non-reproducible, and capable of hallucinating the graph. Explanations in v1 are structured and templated: "this function is imported by 3 files, 2 of which have tests." Correct and dull — exactly the trade being made, and it strengthens the evidence-backed claim. A clean seam is left where an LLM explanation could slot in later, so that version isn't a rewrite.

Why no LLM — the honest version

JobNeeds AI?Why

Reveals — Now, Later, Cut

Cut · 3D visualisation

Hierarchy is the one thing 3D does well, but the core question here is spatial-relationship, and graphs render fastest and clearest in 2D.

Force-directed layout — the algorithm that makes these readable — was designed for 2D. In 3D, nodes spread into a foggy ball with ambiguous depth and occlusion hiding half the graph.

Explainability is the differentiator, and a view where you can't see what's behind what is anti-explainable. A well-animated 2D graph is also more impressive in a demo video than a mediocre 3D one, because motion communicates and orbiting does not.

Cut · The AI in v1

The main concession to PoC scope. Explanations become structured and templated rather than generated — correct, and dull.

This strengthens rather than weakens the differentiator: "no vibes, here's the actual import graph" is a sharper claim than "an LLM told you what might break."

Cut · Repository-wide git activity

"Git activity" and "pull request analysis" were two different inputs in the original idea.

PR analysis is bounded — a known set of changed files. History mining needs a full-repo scan and a time dimension: a different product, answering a different question.

Cut · Monorepo & multi-package support

Real enterprise repos bring workspaces, generated files (dist/, *.d.ts), lockfiles, and scale problems that would eat the budget.

Filtering generated files is still in scope; multi-package resolution is not.

Cut · Deployment

Optional for the hackathon.

The demo runs locally. A public URL isn't needed to satisfy the submission.

Later · Worth doing, not now
  • LLM-generated explanations at the seam left above
  • Repository-wide history mining — hot spots, churn, who changes what
  • Reviewer-optimized annotations
  • Supporting more languages beyond JS/TS
  • Real GitHub API integration instead of pasted input
